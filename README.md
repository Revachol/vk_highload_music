# 1. Тема и целевая аудитория
## 1.1. Тема
### 1.1.1. Тип сервиса
**Музыкальный стриминговый сервис (Spotify)**  

Проектируем музыкальный стриминговый сервис, аналогичный Spotify, с полным функционалом: каталог музыки, персональные плейлисты, рекомендации, социальные функции и кроссплатформенная синхронизация.

**Почему Spotify — это сложная система:**
- 500M+ активных пользователей
- 100M+ треков в каталоге
- 100k+ новых загрузок ежедневно (через Spotify for Artists)
- Реальное время (синхронизация между устройствами)
- ML-рекомендации в реальном времени
- Социальный граф (подписки, совместные плейлисты)

### 1.1.2 Реальные аналоги (доказательство рыночной ниши)
Сервис имеет множество успешных аналогов, подтверждающих огромный рынок:

1. **Spotify** - лидер рынка, 602M MAU (2024) [1]
2. **Apple Music** — 88M подписчиков [2]
3. **Amazon Music** — 82M пользователей
4. **YouTube Music** — 100M+ подписчиков
5. **Яндекс.Музыка** — 50M+ MAU в России и СНГ [3]

**Потенциальный размер аудитории:**  
Общемировой рынок музыкального стриминга — **700M+ активных пользователей** [4].

### 1.1.3. Целевая аудитория (размер и местоположение)
Проектируем сервис для глобального рынка с фокусом на Северную Америку и Европу.

- **Размер:** **100 млн активных пользователей в месяц (MAU)**.
- **DAU (Daily Active Users):** Ожидаем ~40 млн пользователей в день (конверсия 40% из MAU, характерная для музыкальных сервисов).
- **Локализация:** Северная Америка (40%), Западная Европа (35%), остальной мир (25%).
- **Поведение:** Основная активность приходится на утренние (08:00–10:00) и вечерние (18:00–23:00) часы по местному времени, а также на выходные дни.

### 1.1.4. Ключевое продуктовое решение (диверсификация)
Чтобы проект не был "ещё одним клоном Spotify", добавляем **3 уникальных продуктовых решения**, которые есть у реального Spotify, но могут стать нашей диверсификацией:

| Решение | Описание | Сложность реализации |
|---------|----------|---------------------|
| **1. Локальное кэширование + оффлайн-режим** | Треки кэшируются на устройстве. При включении оффлайн-режима пользователь слушает закэшированное. Нужен умный алгоритм предиктивной загрузки (как Spotify: "Your Offline Mix"). | Высокая (ML на клиенте + фоновая синхронизация) |
| **2. Социальные плейлисты (коллаборативные)** | Несколько пользователей могут добавлять треки в общий плейлист в реальном времени (как совместные плейлисты Spotify). Конфликты одновременного редактирования. | Очень высокая (CRDTs / Operational Transforms) |
| **3. Синхронизация между устройствами (Connect)** | Пользователь слушает с телефона, подходит к ПК — одним кликом переносит воспроизведение. Состояние сессии хранится на сервере. | Высокая (управление состоянием в реальном времени) |

## 1.3. Обоснование нетривиальности архитектуры

### 1.3.1. Масштаб данных
- **500M пользователей** — нужно хранить профили, подписки, плейлисты, историю
- **100M+ треков** — метаданные + аудиофайлы
- **2+ млрд плейлистов** создано пользователями [5]
- **100k+ событий в секунду** (лайки, скипы, добавления в плейлисты)

### 1.3.2. Типы нагрузки

| Тип нагрузки | Пример | Масштаб |
|--------------|--------|---------|
| Read-heavy | Поиск, загрузка плейлиста | 1M+ RPS |
| Write-heavy | Лайки, добавление треков | 500k+ RPS |
| Bandwidth-heavy | Стриминг аудио | 100+ Gbps в пике |
| Stateful | Spotify Connect (WebSockets) | 10M+ одновременных соединений |
| Batch processing | Discover Weekly для 500M пользователей | Петабайты данных |

### 1.3.3. Технические вызовы

1. **Глобальная синхронизация состояния**
   - Пользователь слушает на нескольких устройствах
   - Нужно хранить позицию трека, очередь, громкость на сервере
   - Переключение между устройствами должно происходить за <500ms

2. **Рекомендательные системы в реальном времени**
   - Коллаборативная фильтрация (CF) на графе из 500M узлов
   - Контентная фильтрация (анализ аудио, текстов песен)
   - Гибридные модели + A/B тестирование

3. **Обработка событий (Event Streaming)**
   - Каждое действие пользователя — событие
   - Нужно надежно собрать, обработать и сохранить
   - Используем Kafka/Amazon Kinesis

4. **CDN и кэширование**
   - Холодные треки (малопопулярные) хранятся в S3
   - Горячие треки (хиты) реплицируются на PoP-узлы (Edge)
   - Алгоритмы предиктивной загрузки (prefetch) на клиент

5. **Лицензирование и geo-blocking**
   - Разные права в разных странах
   - Трек может быть доступен в США, но недоступен в Германии
   - Нужна быстрая GeoIP проверка при каждом запросе

### 3.4 Схема балансировки

Мы будем использовать гибридную схему для разных доменов.

#### DNS Балансировка (GSLB)
Используется для основного API (api.musicservice.com).
   * Механизм: Latency-based Routing.
   * Как работает: Если пользователь находится посередине между Франкфуртом и Амстердамом, система направит его туда, где в данный момент меньше «пинг» или меньше нагрузка на сервера
   * Резервирование: Если ДЦ во Франкфурте уйдет на обслуживание, DNS просто начнет отдавать всем европейцам IP-адрес Амстердама.

#### Anycast IP
Используется для Edge-узлов (стриминг аудио), статики и CDN.
   * Механизм: Один и тот же IP анонсируется из разных точек мира через протокол BGP.
   * Как работает: Сеть сама «притягивает» запрос пользователя к ближайшему серверу CDN. Это позволяет раздавать 50 ПБ музыки, не перегружая наши основные 5 ДЦ

### 3.5 Механизмы регулировки трафика между ДЦ

Чтобы система была гибкой, мы внедрим Control Plane для управления балансировкой:
   1) Health Checks: Каждый ДЦ сообщает о своей загрузке (CPU, Error Rate, Bandwidth).
   2) Weighted DNS: Если в Европе нагрузка превышает 80%, мы меняем веса в DNS, и 15% новых запросов уходят в США.
   3) Circuit Breaker на уровне Global LB: Если ДЦ не отвечает, GSLB автоматически исключает его IP из выдачи.
   4) Graceful Degradation: В случае экстремальной перегрузки балансировщик может начать отсекать тяжелые запросы (например, рекомендации), оставляя только поиск и стриминг.

# 4. Локальная балансировка нагрузки

### 4.1 Схема локальной балансировки
Разделим на два уровня
##### L4 (Транспортный уровень)
   * Механизм: Работает с IP-адресами и портами. Очень быстрый, потому что не заглядывает внутрь HTTP-пакета.
   * Инструменты: Обычно это железные решения или софт типа IPVS / LVS.
   * Резервирование: Используется схема N+1. Если нам нужно 2 балансировщика, чтобы выдержать поток, мы ставим 3. Если один сгорит, остальные подхватят нагрузку.

##### L7 (Прикладной уровень)
   * Механизм: Работает с HTTP-запросами. Умеет читать куки, заголовки и расшифровывать SSL (HTTPS). Это позволяет отправлять запрос «Поиск» на одни сервера, а «Лайк» — на другие.
   * Инструменты: Nginx, HAProxy или Envoy.
   * Резервирование: Используется схема N*2. Это более дорогое, но надежное резервирование «плечами». Если одна группа (кластер) балансировщиков выйдет из строя, вторая группа имеет 100% запас мощности, чтобы забрать всё на себя.

### 4.2 Расчет количества балансировщиков (для ДЦ в Европе)
* API RPS: 140,000 запросов в секунду.
* Трафик (только API и метаданные): Допустим, ~140 Гбит/с (без учета тяжелого аудио, которое идет через CDN).

##### Ограничитель 1: SSL Termination (Расшифровка HTTPS)
Это самая «тяжелая» операция для процессора на уровне L7. Современный мощный сервер с Nginx может расшифровать (сделать Handshake) и обработать примерно 30,000–40,000 RPS.
Расчет: 140,000 / 35,000 = 4 сервера.
С учетом резерва (N*2): Нам нужно 8 серверов L7 (4 основных + 4 запасных).

##### Ограничитель 2: Пропускная способность сети (Bandwidth)
Это критично для уровня L4. Обычный сервер с быстрым сетевым интерфейсом (NIC) комфортно переваривает 40 Гбит/с.
Расчет: 140 Гбит/с / 40 Гбит/с = 3.5 то есть 4 сервера.
С учетом резерва (N+1): Нам нужно 5 серверов L4.
